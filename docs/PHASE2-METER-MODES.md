# 電錶兩種介接方案:雲端 API vs 地端 Modbus 橋接

> 版本 2026-11-21|系統:**兩套都已實作**,房東在 APP 內自行選擇,可隨時切換
> 月費:雲端 NT$150/月、地端 NT$100/月(以「房源」計,內含該房源所有電錶);硬體另計

## 一、兩種方案的本質差異

| | 方案 A:雲端 API | 方案 B:地端 Modbus |
|---|---|---|
| 誰讀電錶 | 台科電雲端平台讀,我們打 API 拿 | 現場一台小主機讀 RS485/Modbus |
| 現場需要什麼 | 電錶本身能連網(4G/WiFi/有線) | 電錶 + **橋接器**(樹莓派/工控機,約 NT$3,000~8,000) + 配線 |
| 網路要求 | 電錶所在位置要有網路 | 橋接器要有網路(可走房東既有 WiFi/4G) |
| 地下室可用 | ✗(沒訊號就沒資料) | ✓(RS485 可拉線,橋接器放有訊號處) |
| 舊錶可延用 | 需該廠牌支援雲端 | 只要支援 Modbus RTU/TCP 即可 |
| 資料延遲 | 依廠商上報頻率(通常 15~60 分) | 我們自己決定(建議 5 分鐘) |
| 斷電控制 | 依廠商 API 支援 | 直接寫繼電器線圈,最可控 |
| 施工 | 幾乎免施工 | 需現場配線 + 設定橋接器 |
| 誰維護 | 台科電(雲端)+ 我們(API) | **房東/我們(現場主機)**——主機停擺就沒資料 |
| 故障排除 | 遠端即可 | 常需電話指導或到府 |
| 月費 | NT$150/房源 | NT$100/房源 |
| 我們的成本 | API 流量(極低)+ 對接維護 | 現場主機託管 + 遠端診斷 + 到府風險 |

**一句話**:雲端是「房東省事、我們省工」,地端是「房東省月費、我們多工」。

## 二、對定價的意見(建議調整)

你提的 150 / 100 差距只有 NT$50,但**地端的營運成本遠高於雲端**:一台現場主機故障,就是一趟到府或一輪電話排錯,50 元/月撐不住。

| 建議 | 理由 |
|---|---|
| 地端也收 NT$150,雲端收 NT$180 | 反映真實維運成本;價差用「施工費」區隔而非月費 |
| 或維持 100,但**簽 24 期**,並明訂「到府另計 NT$800/次」 | 房東看得到低月費,我們不被單次到府吃掉一年營收 |
| 兩種方案都收**一次性設定費**(雲端 500 / 地端 1,500) | 涵蓋配對、測試、教育訓練 |
| 硬體由房東自購或我們代購(代購加 15%)| 硬體保固責任在廠商,不由我們承擔 |
| 雲端方案的 API 費用轉嫁 | 若台科電另收 API 授權費,外加到雲端月費 |

目前程式已照你的數字實作(150/100),要改只改 `config.php` 兩個常數,不動程式。

## 三、系統架構(已實作)

```
【方案 A 雲端】
  APP → API(meter_sync) → TaikeMeterAdapter → 台科電雲端 → 電錶

【方案 B 地端】
  電錶 ──RS485/Modbus──► 現場橋接器(bridge.py)
                              │ 主動往外(免固定 IP、免開 Port)
                              ▼
                     POST /api/bridge.php?action=push   ← 推讀值(批次)
                     GET  /api/bridge.php?action=poll   ← 拉指令(斷/復電)
                     POST /api/bridge.php?action=ack    ← 回報執行結果
                              │
                              ▼
                     本系統 → 計費 → 帳單 → 通知
```

設計理由:**由現場主動往外連**。若反過來由我們連現場,就得在房東的路由器開 Port、給固定 IP,遇到 CGNAT 直接不可行。現在只要現場能上網就會動。

橋接器認證用 `brg_` 開頭的金鑰(資料庫只存 SHA-256 hash),在 APP 產生、**只顯示一次**,可隨時停用(立即失效)。

## 四、房東在 APP 內怎麼選

`devices.html` → 選房源 →「**電錶介接方案**」卡片:

| 按鈕 | 效果 |
|---|---|
| 雲端 API・NT$150/月 | 該房源所有電錶 adapter 切為 `taike`,月費改 150 |
| 地端橋接・NT$100/月 | 切為 `local_bridge`,月費改 100,並出現「產生橋接器金鑰」 |
| 改回逐台計費 | 回到舊制(每台電錶 NT$100/月) |

切換會**同步改寫該房源所有電錶的 adapter**,避免出現「選了地端卻還在打雲端 API」的矛盾狀態。月費下期帳單起生效(併入 `device_amount`)。

門鎖的 NT$100/台不受影響;方案只取代「電錶逐台計費」那一段。

## 五、橋接器部署(現場)

```bash
# 1. 現場小主機(樹莓派 / 工控機 / 公司電腦)
pip3 install pymodbus requests

# 2. 複製 config.example.json → config.json,填入
#    token(APP 產生)、server、每顆錶的 serial / 通訊參數 / register / scale

# 3. 先拔掉硬體試連線(模擬讀值,不碰 Modbus)
python3 bridge.py --dry-run

# 4. 確認 APP 上「橋接器 在線」且讀值出現 → 再去掉 --dry-run 接真錶
python3 bridge.py
```

**config.json 關鍵欄位**

| 欄位 | 說明 |
|---|---|
| `transport.type` | `tcp`(閘道器/網路型)或 `serial`(RS485 轉 USB) |
| `register` / `function` | 累計度數的暫存器位置;`function` 3=holding、4=input |
| `words` | 32 位元用 2 個暫存器(多數電錶),16 位元用 1 |
| `word_order` | 高低字順序,讀出來是天文數字就改這個 |
| `scale` | 例:暫存器為 0.1 kWh 則填 `0.1` |
| `relay_coil` | 斷復電的線圈位址 |

> ⚠️ **register / scale / relay_coil 必須依實際錶的說明書填**。這三個填錯,讀值會差 10 倍或完全讀不到——這是接案現場最常見的錯誤,先用手持讀錶器或廠商工具核對一次再上線。

**斷復電是「排隊」而非即時**:APP 按下後寫入指令佇列,橋接器下次 poll(預設 60 秒)才執行,結果回寫。這是誠實設計——現場沒連線時不會謊報已斷電。

**開機自動啟動**(樹莓派)
```bash
sudo tee /etc/systemd/system/anhouse-bridge.service <<'EOF'
[Unit]
Description=Anhouse Meter Bridge
After=network-online.target
[Service]
ExecStart=/usr/bin/python3 /home/pi/anhouse-bridge/bridge.py
Restart=always
WorkingDirectory=/home/pi/anhouse-bridge
[Install]
WantedBy=multi-user.target
EOF
sudo systemctl enable --now anhouse-bridge
```

## 七、已知限制

1. **橋接器沒上線就沒有新讀值**:`readLatest` 超過 15 分鐘未回報會直接回報「橋接器已離線,讀值可能不是最新」,不讓舊讀值被當成新資料寫進帳單。
2. **一台橋接器可接多顆錶**(同一 config 的 `meters` 陣列),但目前**一顆錶只能綁一台橋接器**。
3. **Modbus 參數需現場確認**,系統無法自動偵測 register map。
4. **雲端方案仍待台科電憑證**(見 `docs/PHASE2-TAIKE-REQUEST.md`);地端方案**不需等台科電**,只要電錶支援 Modbus 就能先跑。
5. 橋接器目前是單機輪詢,尚無「多台橋接器互為備援」。
