# Phase 1:智慧硬體地基(裝置抽象層 + 門鎖模擬器 + NT$100 加購)

> 版本 2026-11-20|對應《安家生活GO 產品整合架構與設計說明書 v2.1》第九章、第十一章 Phase 1
> 狀態:**程式已完成並通過端到端煙霧測試**,尚未接真實硬體(Aqara 需先簽約取得 API)

## 這一版做了什麼

| 項目 | 說明 |
|---|---|
| 裝置抽象層 | `DeviceAdapter` 介面 + Adapter 工廠;品牌差異不外洩到租約/帳單流程 |
| 門鎖模擬器 | `DevMockLockAdapter`:在 XAMPP 就能跑完整「簽約→發碼→改碼→試開→退租撤權」 |
| Aqara 骨架 | `AqaraLockAdapter`:未設定憑證時一律回「尚未開通」,不製造假成功 |
| 資料表 | `devices` / `device_credentials` / `device_events` / `device_access_logs` / `device_mock_state` + `bills.device_amount` |
| 簽約即發碼 | 租約生效 → 對大門、房門各發一組限時 6 位密碼(租期起~迄),通知房客;大門共用時**每個租約各自一組**(獨立槽位),不共用 |
| 房客自改碼 | **房門**房客可自改;**大門僅屋主/代管管理員/公司管理職可改**(後端強制);弱密碼/同碼/24h 3 次上限;改完即時通知房東與管理職 |
| 退租撤權 | 租約結束 → 該租約所有密碼一次撤銷(鎖端同步失效) |
| 加購計費 | 每台 NT$100/月,自動併入每期帳單(`device_amount`),房客端不加收 |
| 稽核 | 發碼/改碼/撤權/同步/試開 全寫 `device_events`(人、時間、來源、IP);**開門**另寫 `device_access_logs`,可依 6 位密碼反查是誰、開過幾次 |

## 部署(XAMPP)

1. **匯入資料表**
   phpMyAdmin → 選 `idtctw_anhouse` → SQL → 貼上 `database/migrations/20261120_phase1_devices.sql` → 執行。
   可重複執行;`bills.device_amount` 會先檢查是否已存在。
2. **設定金鑰**(`config.php`,本檔已被 .gitignore 排除)
   ```php
   define('DEVICE_PIN_KEY', '<至少 32 字元的隨機字串>');
   define('DEVICE_ADDON_PRICE_MONTHLY', 100);
   define('DEVICE_PIN_CHANGE_LIMIT_24H', 3);
   ```
   未設定也能運作(由 `DB_PASS` 派生),但正式環境請務必設定獨立金鑰。
   Aqara 憑證 `AQARA_APP_ID` / `AQARA_APP_KEY` / `AQARA_BASE_URL` 留空即可,Phase 3 再填。
3. **入口**:會員中心 → 「智慧裝置(門鎖/電錶)」→ `devices.html`
   - 房東/管理員:選房源 → 加裝「大門門鎖」「房門門鎖」(模擬器)→ 顯示加購月費
   - 房客:簽約後於同一頁看到大門/房門密碼,可顯示、修改、試開(模擬)
4. **驗證**:`php tools/devices_smoke_test.php`(需可寫入的測試資料庫)

## 流程

```
租約建立(pending)
   └─ 房客接受 → leases.status=active
        ├─ generate_lease_bills()          ← 首期帳單(含 device_amount 加購)
        └─ device_issue_for_lease()
             ├─ 逐把門鎖 role=gate/door → device_gen_pin()
             ├─ adapter->setPin(鎖端寫入,模擬器寫 device_mock_state)
             ├─ device_credentials(pin_hash + pin_enc,有效起迄=租期)
             └─ notify(房客:入住開鎖碼已開通)

房客改碼 → device_change_pin()
   ├─ 權限(本人或管理端)+ 租約仍生效
   ├─ 弱密碼/同碼檢查 + 24h 3 次上限
   ├─ adapter->setPin(鎖端覆寫,舊碼即刻失效)
   ├─ device_events(pin_changed)
   └─ notify(房東/管理職/業務:密碼已變更)

租約結束 → device_revoke_for_lease()
   ├─ adapter->revoke(每個槽位)
   ├─ credentials → expired
   └─ notify(房客:權限已撤銷)
```

## API(`api/devices.php`)

| 方法 | 動作 | 權限 |
|---|---|---|
| GET | `?action=my` | 房客:生效租約的門鎖 + 自己的密碼 + 紀錄 |
| GET | `?action=properties` | 可管理房源清單(含裝置數) |
| GET | `?action=property&property_id=` | 房源裝置、憑證、事件、加購費 |
| POST | `add` / `remove` / `sync` | 屋主、代管管理員、公司管理職(業務唯讀) |
| POST | `issue`(lease_id) | 同上;重新發碼(換房客/沒收到) |
| POST | `change_pin`(credential_id,new_pin) | 憑證持有人或管理端 |
| POST | `revoke_pin` | 憑證持有人或管理端 |
| POST | `mock_unlock` | 模擬鎖試開驗證 |

## 安全設計

- 密碼**不存明文**:`pin_hash`(password_hash)供驗證,`pin_enc`(AES-256-GCM,金鑰 `DEVICE_PIN_KEY`)僅供持有人/管理端在 APP 內查看;正式品牌鎖由鎖端保存,平台不應也不需要回讀。
- 模擬器的明文只存在 `device_mock_state`,且標註為開發用途;**不得**在正式環境使用 `dev_mock` 對外。
- 改碼頻率限制以 `device_events` 實測計算(非前端計數,無法繞過)。
- 退租/換約/移除裝置三條路徑都會呼叫 `adapter->revoke()`,避免「平台說失效、鎖端還能開」。
- 大門(`role=gate`)跨戶共用,權限一律 `tenant_editable=0`:只有屋主、代管管理員、公司管理職可發/改/撤,房客端看得到號碼但改不了(後端每次檢查,非前端隱藏)。房門(`role=door`)房客可自改,改碼會通知所有管理關係人(屋主、代管、公司管理職、業務),降低同住人遭鎖門外的風險。

## 大門共用與「每人一組」(代管人員操作規則)

> 2026-11-20 起適用。這一節是給實際操作的代管/櫃台人員看的,照著做就不會出現「不知道是誰開的門」。

### 為什麼大門要每人一組

同一道大門、樓道門有多戶共用時,若大家共用一組密碼,事後無法回答「昨晚是誰開的門」。提前解約、押金爭議、公共物品損壞、遺失鑰匙,都需要提得出人。

因此規則:**大門一律每人一組**——每個租約在鎖上佔一個**獨立槽位**,各自一組 6 位碼。一層三戶就是三個槽位,互不覆蓋;退租只撤掉自己那一個,同層其他人完全不受影響。

共用一組只在特定情境開啟(見「何時才開共用碼」),預設關閉。

### 兩種門的權限(後端強制)

| 角色 | `role` | 說明 | 房客可自改 |
|---|---|---|---|
| 大門 / 樓道門 | `gate` | 跨戶共用,同層或整棟住戶都會經過 | ✗ 只有屋主、代管管理員、公司管理職可改 |
| 房門 | `door` | 該戶專用 | ✓ 房客可自改(仍有弱密碼/同碼/24h 3 次限制) |

房客在 APP 看得到自己的大門碼(要用),但沒有修改、撤銷按鈕;就算直接呼叫 API 也會被後端擋下。

### 槽位命名(稽核紀錄裡看得到)

每組憑證在鎖上有一個獨立槽位代號 `slot_ref`,格式固定:

| 槽位 | 意義 |
|---|---|
| `gate:l11` | 租約 #11 的大門碼 |
| `door:l11` | 租約 #11 的房門碼 |
| `gate:shared` / `door:shared` | 共用碼(開啟共用模式時才存在) |
| `manager` | 屋主 / 管理員專用碼(不是租約) |

看到 `gate:l9` 就知道是租約 #9 那戶的大門碼;要看租約對應誰,到租約頁查 #9 即可。這也是接真鎖後唯一的對應依據(真鎖只回報「哪個槽位開門」,不會告訴你人名)。

### 操作步驟

**加裝大門門鎖**
1. 房源頁 → 加裝「大門門鎖」,選樓道門/整棟門
2. 系統對該範圍內**所有生效中的租約**逐一發碼,一戶一組(不會只發給第一個)
3. 發完在房源頁核對「大門密碼」清單:戶數 = 在租租約數,少一組就是有租約沒生效,先去修租約

**新租約**
- 租約生效時自動補發大門 + 房門各一組,不用手動加

**交屋交付**
- 密碼在房客 APP 內可自行查看,也可當面告知
- **不要**在住戶群組貼出全部人的碼,等於回到共用碼

**換房客**
- 對該租約按「重新發碼」,舊碼立即失效
- 不要手動改數字、也不要沿用前一位房客的碼

**退租**
- 系統自動撤銷該租約所有槽位(gate + door),鎖端同步失效
- 同層其他住戶的碼不動;房東需確認房客 APP 已看不到舊碼

### 何時才開共用碼

只有這幾種情況建議開,其餘一律每人一組:

- 房東自住、沒有租約的門
- 日租 / 短租,換人頻繁且不做進出稽核
- 施工、清潔、搬運等臨時人員(**用完立刻關閉**)

開關方式:房源頁「👥 共用碼」按鈕(或 API `set_shared_pin`)。

⚠️ 共用碼**不能單獨撤銷**,必須先關閉共用模式才會失效。這是刻意設計:避免「以為撤了、其實門還開著」。臨時人員用完請直接關閉,不要只換數字。

### 費用:共用的一次,不重複收

每台裝置 NT$100/月**只收一次**,不按戶數均攤:

| 裝置範圍 | `scope_type` | 計入哪張帳單 |
|---|---|---|
| 房門 | `unit` | 該戶帳單 |
| 樓層樓道門 | `floor` | 只收一次;歸屬 `charge_property_id` 指定的那一戶,`NULL` = 房東自負 |
| 整棟共用門 | `building` | 同上 |

實例(快樂街 12 號):301 / 302 / 303 各 NT$100(自己的房門);3F 樓道門 NT$100 **只收一次**、目前由房東負擔 → 房客帳單不會出現重複的樓道門費。若某戶反應「怎麼被收了兩次門鎖費」,先查該筆的 `scope_type` 與 `charge_property_id`,幾乎都是範圍設錯。

### 進出稽核

房源頁最下方「進出紀錄(開門稽核)」:

- 每筆顯示:時間 / 哪一道門 / 大門或房門 / 密碼末四碼 / 對應房客 / 租約編號
- 上方反查框輸入 **6 位密碼** → 顯示這是誰的碼、用這組碼開過幾次
- 權限:該房源的屋主、代管管理員、公司管理職可看;業務唯讀
- 密碼只存雜湊,反查是拿你輸入的碼去比對雜湊,系統不回存明文密碼

隱私守則:

- 紀錄只提供給有管理關係的人,不對外公開
- 對外(報警、調解、律師)只提供**該人、該時段**的紀錄,不要整份匯出給無關第三人
- 目前不自動刪除;建議爭議期滿(退租後 6 個月)再清理

### 常見狀況排除

| 症狀 | 處理 |
|---|---|
| 房客說密碼打不開 | ① 租約是否生效 ② 碼是否被改過(改過舊碼即失效) ③ 查進出紀錄有無失敗嘗試 ④ 必要時重新發碼 |
| 兩戶拿到同一組碼 | 不該發生(每租約獨立槽位);若出現,檢查該憑證 `slot_ref` 是否為空,回報工程 |
| 反查顯示查無此密碼 | 可能是共用碼,或已撤銷的舊碼;已撤銷的碼查不到是正常的 |
| 房客端沒有「改碼」按鈕 | 正常:大門(`gate`)為管理端專用,房客只能看 |
| 退租後仍有人開門 | 查進出紀錄看是哪個槽位;若是 `gate:shared`,代表共用模式還開著,請關閉 |

### 真鎖的限制(別對房東過度承諾)

目前是**模擬鎖**:開門紀錄在系統試開時產生,可用來驗證流程與介面,不是真實住戶的進出。

接 Aqara 真鎖後,雲端通常只回報「哪個槽位開門」——我們用 槽位 → 租約 → 房客 對應,仍可查到人;前提是先完成 Aqara 簽約取得 AppID/AppKey,並開通事件回傳。在開通前,`fetchEvents()` 一律回「尚未開通」,介面不會假裝有紀錄。

對外說法建議:「系統可查某組密碼對應的住戶與開門時間」,不要說成「可以看所有開門影像/即時通知」。
