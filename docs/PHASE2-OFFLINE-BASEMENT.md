# 地下室案場避坑指南(離線優先的電錶方案)

> 版本 2026-11-21|對象:安裝人員、代管、業務報價
> 先講結論:**「地下室沒網路」不是一種情況,是三種**,處理方式與報價都不同。

## 一、先分清三種案場(決定要不要賣地端)

| 案場 | 判斷方式 | 建議方案 | 月費 |
|---|---|---|---|
| **A. 電錶位置有網路** | 手機在電錶旁測速 ≥ 5 Mbps | 台科電雲端 API(不需現場主機) | NT$150 |
| **B. 電錶位置沒訊號,但同棟有** | 手機在地下室無訊號,走到 1F/樓梯間有 | RS-485 拉線 + 4G 閘道器(放訊號處)or 工控機 | NT$100 |
| **C. 整棟/整區完全無網路** | 連 1F 都沒訊號、無固網 | 離線橋接:現場自行扣款斷電,定期回傳 | NT$100 + 到府同步 |

**業務最常犯的錯**:把 C 當 B 賣。C 的現場主機拿不到雲端政策,如果程式只會「讀值上報」,那台機器就是廢鐵——帳不會算、電不會斷。所以 C 一定要用**離線優先**版本。

## 二、你的兩個判斷,我補三個實務細節

### 1.「地端不能只靠純本地電腦」——正確,而且這是產品定位問題

如果資料只留在現場電腦,房東在外面打開 APP 看到的是空白。這不是 bug,是契約問題:必須在合約寫明「**C 案場為離線帳本,度數以現場主機為準,APP 顯示最後同步時間**」。

APP 端一定要顯示三件事,否則房東會以為壞了:
- 最後同步時間(例:3 天前)
- 目前為「離線帳本」狀態
- 未回傳筆數(例:128 筆待補傳)

### 2.「4G 閘道器」與「迷你工控機跑 C#」是兩種不同的東西

| | RS-485 → 4G 閘道器 | 迷你工控機 / 樹莓派 |
|---|---|---|
| 成本 | NT$2,500~5,000 | NT$3,000~8,000 + SIM + 電源 |
| 能做什麼 | 透傳 Modbus,雲端主動來讀 | 可自行判斷、扣款、斷電、本地存帳 |
| 適用的案場 | **B**(有網路) | **B 與 C** |
| 誰維護 | 廠商 | 你(或代管) |
| 風險 | 韌體 bug、雲端綁定費 | 停電/當機/記憶卡壞 → 需 watchdog |

**建議**:B 案場兩種都能用,但**統一用同一種硬體**(工控機)對維運最省事——備品一套、腳本一套、教學一套。差價用一次性施工費吸收。

### 3. C 案場的「定期走進地下室」要嘛自動化,要嘛別賣

手動同步的問題不是技術,是**人**:房東三個月不下去,帳本三個月沒回傳,那段時間的爭議完全沒有雲端紀錄可查。

三種解法,按推薦順序:
1. **主機自帶 4G + 外接天線拉到地面**(最推薦):天線 5 米線拉到窗邊/管道間,成本約 NT$1,500,就能從 C 變 B。
2. **主機開 Wi-Fi AP + 手機自動同步**:房東回家連到該 Wi-Fi 就自動補傳(APP 背景同步),不必「走進地下室」。
3. **換記憶卡/隨身碟**:最原始,只在完全無法妥協時用。

## 三、離線帳務的四條鐵律(程式已實作)

這四條是為了避免「離線扣一次、上線又扣一次」把房客的錢扣光:

| 鐵律 | 實作 | 為什麼 |
|---|---|---|
| ① 現場是唯一扣款者 | `device_meter_state.authority='agent'`,雲端 `meter_deduct_usage` 直接跳過 | 兩邊都算 = 扣兩次 |
| ② 每筆帳務有 uuid | `meter_ledger.uuid` UNIQUE | 斷線重試幾十次也只入帳一次 |
| ③ 有未同步帳本時不套用雲端餘額 | 同步前先查 `synced=0` 筆數 | 否則現場已扣的錢會「復活」 |
| ④ 儲值要等現場連線才生效 | `meter_topups.applied_at` + policy 的 `credits` | 離線時儲值不可能即時復電,誠實標示 |

**第 ④ 條要跟房東講清楚**:C 案場的「儲值後立即復電」做不到。若房東堅持要即時復電,他需要 B 案場(有網路)。

## 四、硬體配置建議(BOM)

### B 案場(有訊號)
| 項目 | 規格 | 參考價 |
|---|---|---|
| RS-485 電錶 | 台科電或支援 Modbus RTU 的錶 | 依廠商 |
| RS-485 匯流排 | 屏蔽雙絞線 0.75mm²,菊花鏈,末端 120Ω 終端電阻 | NT$15/m |
| 4G 閘道器 或 工控機 | 支援 Modbus RTU 主站 | NT$2,500~8,000 |
| 4G SIM | 物聯網卡,月租 NT$99~199 | 月費 |
| 電源 | 電箱內 5V/12V 適配器 + 不斷電(小 UPS) | NT$300~1,200 |
| 外接天線 | 5dBi~8dBi,線長 5m | NT$800~1,500 |

### C 案場(完全無網)
B 的全部,外加:
| 項目 | 說明 |
|---|---|
| 離線主機 | 樹莓派 4/5 或工控機,**必須有 watchdog** |
| 本地儲存 | SD 卡容易壞 → 用工業級 SD 或 SSD |
| 本地 Wi-Fi AP | 讓房東手機在現場直連看度數(程式已內建 LAN 服務) |
| 定期巡檢 | 每季一次,檢查 `pending` 筆數與硬碟空間 |

**成本提醒**:C 案場的月費 NT$100 幾乎一定虧。建議 C 案場加收「現場維護費」NT$500/季,或直接把月費拉到 NT$200。

## 五、現場安裝檢查清單(照著勾)

```
□ 手機在電錶位置測速(記錄 Mbps)→ 決定 A/B/C
□ 電錶 Modbus 參數抄下來:slave id / register / function / words / scale / relay coil
□ 用手持讀錶器或廠商工具核對讀值(必須與電錶面板一致)
□ RS-485 接線: A/B 不接反、末端電阻、屏蔽層單端接地
□ 主機通電測試,確認指示燈與 `python3 bridge.py --dry-run` 可跑
□ 填入 config.json 的 token(APP 產生,只顯示一次)
□ 上線後在 APP 確認:橋接器「在線」、讀值出現、與面板一致
□ 測試斷電 → 現場確認真的斷 → APP 看 relay_state=off
□ 測試恢復 → 儲值 → 確認自動復電
□ 設定 systemd 開機自動啟動 + watchdog
□ 貼標籤:主機位置、IP、聯絡窗口
```

## 六、實測紀錄(2026-11-21)

| 測項 | 結果 |
|---|---|
| 離線扣款 | 現場讀值差 × 單價 → 寫入本地 ledger,餘額正確遞減 |
| 冪等補傳 | 同一批帳本重送 → `accepted: 0, duplicate: N`,餘額不動 |
| 讀值冪等 | 同一 uuid 重推 → 第二次 `ignored` |
| 雲端不重扣 | `authority=agent` 時 cron 回「由現場自行扣款,雲端不重複扣抵」 |
| 離線儲值補套用 | policy 回 `credits` → 現場套用後回報 `topup`,雲端標記 `applied_at` |
| 本地區網服務 | `GET /status` 回讀值/餘額/待傳筆數;`POST /relay` 可現場斷電並排入補傳 |

## 七、C# 版說明(給你們團隊)

`tools/meter-bridge-cs/` 是移植骨架,**本沙箱無 dotnet SDK,未經編譯驗證**。
資料表結構、uuid 規則、API 契約與 Python 版完全一致,兩者可共用同一個 `bridge.db`。
`Meters.cs` 的 NModbus 連線留了 `NotSupportedException` 與接法註解——請照 README 補完並在實機測試。

**已驗證可運作的是 Python 版**(`tools/meter-bridge/bridge.py`),建議先用它跑通一個案場,再決定要不要花工移植。
