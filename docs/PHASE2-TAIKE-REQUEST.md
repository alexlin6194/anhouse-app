# 向台科電索取資料清單(Phase 2 電錶串接)

> 用途:把這份直接轉給台科電窗口,回來的資料填進 `anhouse_private/secrets.php` 即可上線。
> 我方目前狀態:抄表、計費、出帳、儲值斷電**全流程已完成並在正式站跑通**(模擬電錶),
> 唯一缺口是台科電的連線憑證與 API 規格。

---

## 一、先問清楚:你們有沒有「對外 API」

這是整件事的前提,請對方明確回答「有 / 沒有 / 需另外付費開通」:

| 問題 | 為什麼要問 |
|---|---|
| 電錶資料是否上傳到你們的雲端平台? | 若只做本地 RS485,就必須另裝閘道或改走 Modbus |
| 有沒有提供 HTTP/REST API 給客戶系統介接? | 我們需要主動查讀值,不能只靠你們的 App |
| API 是否需要另外簽約或付費? | 影響報價與時程 |
| 有沒有測試環境(沙箱)與測試錶? | 沒有沙箱就只能拿正式錶試,風險高 |

若答案是「只有 App、沒有 API」,請直接跳到最後一節〈沒有 API 的替代方案〉。

## 二、技術資料索取清單(逐項都要)

### 1. 連線與認證
- [ ] **API Base URL**(測試環境 / 正式環境,分開列)
- [ ] 認證方式:API Key?HMAC 簽章?OAuth2 Client Credentials?
- [ ] 簽章字串的**組法與順序**(例:`key + timestamp + path`,順序錯就全部 401)
- [ ] 簽章演算法(SHA256 / SHA1 / MD5)與**編碼方式**(hex / base64)
- [ ] 時間戳格式(秒 / 毫秒)、允許誤差秒數、是否需 UTC
- [ ] 金鑰輪替(rotate)方式與有效期
- [ ] 是否需要**綁定來源 IP 白名單**(我方固定 IP:`203.99.146.66`)
- [ ] 是否需要 TLS 用戶端憑證(mTLS)

### 2. 端點(每一支都要:方法、路徑、參數、完整回應範例)
- [ ] **即時讀值**:單一電錶最新度數
- [ ] **歷史讀值**:可指定時間區間;能否一次多錶?
- [ ] **批量查詢**:整批電錶最新讀值(幾十戶時很關鍵,逐台查會被限流)
- [ ] **設備清單**:回傳序號、型號、安裝狀態、在線/離線
- [ ] **繼電器控制**(斷電 / 復電)—— 儲值型電錶必要
- [ ] **事件 / 告警**:停電、斷線、開蓋、超載、餘額不足
- [ ] 是否有 **Webhook 主動推播**?回呼網址怎麼設定、重試機制為何?

### 3. 資料格式(最容易出錯的地方)
- [ ] 讀值單位:度(kWh)還是 Wh?**是否需除以 1000**
- [ ] 小數位:整數或 1~2 位小數?(我方資料庫存整數度,需確認四捨五入規則)
- [ ] 讀值遞增型(累計度數)還是區間用量型?
- [ ] `read_at` 時區:UTC 或 UTC+8?格式(ISO8601 / `YYYY-MM-DD HH:MM:SS`)?
- [ ] 電錶序號規則(長度、英數、是否含前導零)
- [ ] 一戶是否可能有多個迴路 / 多錶(總錶 + 分錶)?如何歸戶

### 4. 營運限制
- [ ] 讀值更新頻率(每 15 分?每小時?)與**資料延遲**(呼叫後拿到的是幾分鐘前的資料?)
- [ ] 呼叫限流:每秒 / 每分鐘 / 每日上限
- [ ] 歷史資料保留期間(可回溯幾個月?)
- [ ] **斷線補讀**:電錶離線期間的資料,恢復後會不會補齊?
- [ ] 完整**錯誤碼表**(含限流、維護中、設備離線的專屬代碼)
- [ ] 維護窗口與 SLA(可用率承諾)

### 5. 計價方式(最關鍵,決定我方定價底線)

- [ ] API 授權費的**計價單位**是:①按電錶顆數 ②按開發商帳號固定年費 ③按呼叫次數?
- [ ] 若是按顆數:單價多少?**是否有階梯價**(例 500 顆、1,000 顆以上)?
- [ ] 若是按帳號固定年費:年費多少?**有無最低顆數門檻或成長期優惠**?
- [ ] 按呼叫次數者:每千次多少?**抄表頻率**(每 5 分鐘 vs 每小時)是否影響費用?
- [ ] **合約期間內的調價機制**:可否單方調價?調價上限?多久前通知?
- [ ] 是否另收「開通費 / 系統整合費 / 客製對接費」?
- [ ] 報價是否含稅?發票形式(二聯/三聯/電子發票)?
- [ ] 若我方客戶數成長 10 倍,費率是否重新議約?

> ⚠️ **這一節沒問清楚前不要對外報價**。若對方是按「開發商帳號固定年費」,
> 初期 20 戶的營收可能全部付給對方;若是按顆數,則可隨客戶數等比成長,風險可控。
> 另外務必問「合約期內調價機制」——三年後對方漲一倍,我方已簽給房東的月費會變成負毛利。

### 6. 商務與資安
- [ ] 資料所有權:讀值資料歸我方或貴方?合約終止後能否匯出?
- [ ] 個資與用電資料的處理方式(是否會用於貴方其他用途)
- [ ] API 金鑰洩漏的通報與停用流程

## 五、拿到資料後的驗收(我方執行,不需廠商配合)

1. **讀值一致性**:同一時間點,API 讀值 vs 電錶面板顯示,誤差需為 0 度
2. **時區正確性**:`read_at` 換算後與台北時間相符(曾在其他專案遇過差 8 小時導致整月帳單錯位)
3. **連續抄表**:連續呼叫 3 次,讀值不倒退、不重複寫入
4. **歷史回補**:查昨日區間,筆數與預期更新頻率相符
5. **斷復電**:控制後確認 `relay_state` 與現場一致(需有人在現場確認)
6. **限流**:壓測到對方上限,確認我們有退避重試、不會把帳單算錯
7. **錯誤處理**:故意用錯金鑰 / 錯序號,確認系統回報清楚且**不會寫入假讀值**

驗收通過後把三行設定填進 `anhouse_private/secrets.php`:
```php
'TAIKE_BASE_URL'   => 'https://...',
'TAIKE_API_KEY'    => '...',
'TAIKE_API_SECRET' => '...',
```
`TaikeMeterAdapter` 會自動接手,其餘流程(抄表→計費→出帳→通知)不需改動。
若對方規格與現行假設不同(端點路徑、欄位名稱、簽章字串),只需改 `TaikeMeterAdapter` 的三個方法。

## 六、沒有 API 的替代方案

| 情境 | 做法 | 代價 |
|---|---|---|
| 電錶只有 RS485 / Modbus | 加裝 4G 工業閘道(如 USR/有人物聯),由我方或廠商寫 Modbus 輪詢 | 每戶一次性硬體費 + 需現場配線 |
| 只有廠商 App、不開放 API | 無法自動抄表;改為每月人工抄錄,系統已支援手動輸入讀值 | 人力成本,但帳單邏輯不變 |
| 電錶可換 | 換成有開放 API 的錶(台科電或他家),重新議價 | 換錶成本,長期最省事 |
| 只用脈衝輸出 | 加裝脈衝計數器 + 閘道,自行累計度數 | 精度取決於錶的脈衝常數,需校正 |

> 不論走哪一條,**現有系統都不必重寫**:`MeterAdapter` 介面已把品牌差異隔離,
> 新增一種錶只要多寫一個 adapter 類別。
